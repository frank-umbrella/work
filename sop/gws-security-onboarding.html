1.Purpose

This SOP establishes the standard Google Workspace security configuration to be applied when onboarding a new client. The goal is to provide a consistent baseline for password security, multi-factor authentication, passkeys, administrator protection, and Organizational Unit structure.

2.Scope

This procedure applies to every new Google Workspace tenant Umbrella Automation onboards, and to existing tenants being brought up to the standard baseline. It covers Organizational Unit structure, password policy, 2-Step Verification, passkeys, Super Admin protection, account lifecycle (creation, offboarding), and service accounts. It does not cover email routing, device management, or third-party app access, which are handled separately.

3.Definitions

TermMeaning
OU (Organizational Unit)A container in the Google Admin Console used to group users and apply policies. Child OUs inherit settings from their parent unless overridden.
2SV (2-Step Verification)Google's multi-factor authentication. A second proof of identity (prompt, authenticator code, passkey, or security key) required at sign-in.
PasskeyA phishing-resistant FIDO credential unlocked by the user's device (Windows Hello, Face ID, Touch ID, Android, or a hardware key) instead of a typed code.
Super AdminA Google Workspace account with full administrative control of the tenant.

4.Procedure

4.1Create or Review Organizational Units

Navigate toGoogle Admin Console›Directory›Organizational Units

Recommended baseline structure:

  • Company / Root OU
    • Users
    • Admins
    • Service Accounts
    • Suspended / Former Users

Additional OUs may be created when required for specific departments, locations, or policy differences.

Standard practice: apply the primary security baseline at the top-level/root OU whenever possible. Child OUs should inherit these settings unless there is a specific business or technical reason to override them.

4.2Configure Password Policy — Standard Users

Navigate toSecurity›Authentication›Password management

Select the appropriate Organizational Unit, then configure:

SettingValue
Minimum password length15 characters
Maximum password length100 characters
Enforce strong passwordEnabled
Allow password reuseDisabled
Password expirationNever
Enforce password policy at next sign-inEnable during initial deployment when existing passwords do not meet the new requirements

Password policy notes

Users should be encouraged to use long, unique passwords or passphrases instead of short passwords with predictable substitutions. Example of a stronger passphrase: Coffee Table Bears Dance 27

Avoid requiring periodic password changes solely because a password has reached a certain age. Passwords should instead be changed when:

  • A password is known or suspected to have been compromised
  • A security incident has occurred
  • Credentials were accidentally disclosed
  • An administrator determines an account may have been accessed improperly

4.3Configure Password Policy — Administrators

Create or use a dedicated Admins OU for administrator accounts.

Navigate toSecurity›Authentication›Password management

Select the Admins OU, then configure:

SettingValue
Minimum password length16–20 characters
Maximum password length100 characters
Enforce strong passwordEnabled
Allow password reuseDisabled
Password expirationNever
2-Step VerificationRequired
PasskeysAllowed
Hardware security keysStrongly recommended for Super Admin accounts
No shared admin credentials. Administrator accounts should never use shared credentials. Each administrator should have their own named administrative account whenever possible.

4.4Enable 2-Step Verification

Navigate toSecurity›Authentication›2-Step Verification

Select the top-level Organizational Unit, then configure:

SettingValue
Allow users to turn on 2-Step VerificationEnabled
EnforcementEnabled
Authentication methodsAllow approved 2-Step Verification methods
PasskeysAllow where supported

New client rollout

When onboarding an existing organization where users have not yet enrolled in 2-Step Verification:

  1. Enable 2-Step Verification enrollment.
  2. Notify users that enrollment is required.
  3. Provide users with an enrollment deadline.
  4. Confirm administrator accounts are enrolled first.
  5. Configure the enforcement date.
  6. Monitor user enrollment.
  7. Enforce 2-Step Verification for remaining users after the enrollment period.
Lockout risk: do not immediately enforce 2-Step Verification before confirming that Super Admin accounts have working authentication and recovery methods.

4.5Configure Passkeys

Allow users to enroll passkeys where supported. Passkeys may use:

  • Windows Hello
  • Face ID
  • Touch ID
  • Android device authentication
  • Hardware security keys
  • Other supported FIDO-compatible authentication methods

Benefits

  • Strong phishing resistance
  • No authentication code for users to manually enter
  • Reduced reliance on passwords
  • Faster authentication
  • Protection against password reuse and credential theft

Allowing passkeys does not necessarily require immediately converting the organization to passwordless authentication.

Recommended policy: for general users, allow passkeys while continuing to require 2-Step Verification. For administrators, strongly encourage passkeys or physical security keys.

4.6Protect Super Admin Accounts

All Super Admin accounts must have multiple recovery/authentication methods configured. Recommended configuration:

  • Strong unique password of at least 16–20 characters
  • 2-Step Verification enabled
  • Passkey or hardware security key configured
  • Backup verification method available
  • Backup codes stored securely
  • At least two Super Admin accounts maintained when appropriate
Single point of failure: do not rely on a single mobile phone as the only authentication method for a Super Admin account.

4.7Review User 2-Step Verification Enrollment

During onboarding, verify that users are successfully enrolling in 2-Step Verification. Navigate to the applicable Google Admin security reporting area and review:

  • 2-Step Verification enrollment
  • Accounts without 2-Step Verification
  • Administrator enrollment
  • Suspicious login activity
  • Password security warnings

Users who have not completed enrollment should be contacted before final enforcement whenever practical.

4.8User Account Creation Standard

When creating a new Google Workspace user:

  1. Create the user in the appropriate Organizational Unit.
  2. Assign the appropriate Google Workspace license.
  3. Generate a temporary password.
  4. Require the user to change the temporary password at first login.
  5. Confirm the resulting password complies with the organization's password policy.
  6. Require 2-Step Verification enrollment.
  7. Encourage passkey enrollment.
  8. Verify account recovery information when appropriate.
  9. Confirm the user has access only to required applications, groups, and resources.

4.9Former Employee / Terminated User Procedure

When a user leaves the organization:

  1. Reset the user's password if immediate access termination is required.
  2. Revoke active sessions.
  3. Remove application-specific passwords and authentication tokens where appropriate.
  4. Remove or review passkeys and security keys.
  5. Suspend the Google Workspace account.
  6. Transfer ownership of required Google Drive files.
  7. Transfer or delegate required email information according to company policy.
  8. Remove the user from groups and shared resources as appropriate.
  9. Move the account to the Suspended / Former Users OU, if used.
  10. Delete the account only after data retention and transfer requirements have been satisfied.

4.10Service Accounts and Shared Accounts

Avoid shared usernames and passwords whenever possible. Instead, use:

  • Google Groups
  • Shared mail routing
  • Delegated mailbox access
  • Application-specific service accounts
  • Role-based permissions

If a dedicated service account is required:

  • Place it in the Service Accounts OU
  • Use a long randomly generated password
  • Do not share the password unnecessarily
  • Restrict interactive login whenever possible
  • Limit permissions to only those required
  • Document the account's purpose and owner

4.12Final Onboarding Verification

Before considering Google Workspace security onboarding complete, verify:

  • Organizational Units have been created or reviewed
  • Root OU security policies are configured
  • User password minimum is set to 15 characters
  • Strong password enforcement is enabled
  • Password reuse is disabled
  • Password expiration is disabled
  • Admin OU has stricter security requirements
  • 2-Step Verification is enabled
  • 2-Step Verification enforcement is configured
  • All Super Admin accounts are enrolled in 2-Step Verification
  • Super Admin backup authentication methods are configured
  • Passkeys are allowed
  • Administrator passkeys/security keys are configured or recommended
  • User 2-Step Verification enrollment has been reviewed
  • Shared account usage has been reviewed
  • Service accounts have been identified and documented
  • Former-user account procedures are established
  • At least two authorized administrators are documented where appropriate

5.Standard Security Baseline Summary

For most new Google Workspace clients, the default configuration should be:

Baseline: 15-character passwords + Google strong-password enforcement + no password reuse + no routine password expiration + mandatory 2-Step Verification + passkeys allowed.

Administrator accounts should receive additional protection through longer passwords, multiple recovery methods, passkeys, and preferably hardware security keys.
